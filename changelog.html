wp-core.sh1.6.12026-09-03
  • Fixed a fresh install failing on cPanel with Cpanel::Exception::IO::FileNotFound when the generated database password happened to start with @. cPanel's apitool reads an argument value beginning with @ as @filename and tries to load that file, so Mysql create_user died before the database user was ever created. Generated passwords now always start with a letter or a digit — the rest of the character set, symbols included, is unchanged, so nothing is lost in strength.
  • A fresh install no longer trips over leftovers from a half-finished run: an existing database is reused and an existing database user is kept and given the new password (Mysql set_password) instead of aborting with “already exists”. Both cases are announced on the progress line.
  • رفع خطای نصب تازه روی cPanel با پیام Cpanel::Exception::IO::FileNotFound وقتی رمز تولیدشدهٔ دیتابیس تصادفاً با @ شروع می‌شد. ابزار apitool در cPanel مقداری را که با @ شروع شود به‌عنوان @filename می‌خواند و سعی می‌کند آن فایل را باز کند، برای همین Mysql create_user پیش از ساخته‌شدن کاربر دیتابیس شکست می‌خورد. حالا رمزهای تولیدی همیشه با حرف یا رقم شروع می‌شوند — بقیهٔ مجموعهٔ کاراکترها از جمله نمادها دست‌نخورده است و چیزی از قدرت رمز کم نمی‌شود.
  • نصب تازه دیگر با باقی‌ماندهٔ یک اجرای ناتمام گیر نمی‌کند: دیتابیسِ موجود دوباره استفاده می‌شود و کاربرِ موجود هم نگه داشته شده و رمز جدید روی آن ست می‌شود (Mysql set_password) به‌جای اینکه کار با پیام «already exists» متوقف شود. هر دو حالت روی خط پیشرفت اعلام می‌شوند.
wp-core.sh1.6.02026-09-02
  • Administrator management no longer runs PHP. It reads the credentials out of wp-config.php and talks to MySQL directly — nothing bootstraps WordPress and no plugin code is executed, so the server's php binary being a different version than the site expects can no longer fatal the operation. Connection details are taken from DB_HOST (host, host:port or host:/socket, with PHP string escapes decoded), the real $table_prefix is honoured, and if the configured host does not answer the common socket paths and the TCP loopback are tried in turn. The password reaches mysql through MYSQL_PWD instead of the command line, and --no-defaults stops a stray ~/.my.cnf from hijacking the login. A password change now also clears the account's session_tokens, signing every other session out. New passwords are written in WordPress's legacy MD5 format, which WordPress accepts and silently upgrades to its modern hash on the first sign-in.
  • Creating an administrator now suggests the login: the first free name in the admin, admin1, admin2… series is worked out in a single query and shown in parentheses, and pressing Enter accepts it. Added --admin-user <u>, --admin-email <e> and --admin-pass <p> to create one with no prompting at all — each implies -A, and -A -y fills in every default. When no login is given, flag mode falls back to the same suggestion.
  • The real login URL is now reported next to the WordPress version and in the administrator submenu header, read straight from wp_options. If a plugin has moved wp-login.php the moved address is shown along with the plugin responsible — WPS Hide Login, Rename wp-login.php, Hide My WP Ghost, All In One WP Security, Defender, WP Cerber, Perfmatters or Solid Security. If none of those options is present but active_plugins still lists a login-hiding plugin, the default address is shown with a warning to verify it. A siteurl/home mismatch is called out on its own line.
  • Generated passwords are now fully random. The old helper appended a fixed Xy9@#, pinning the last five characters and leaking the pattern; every character now comes from /dev/urandom and the candidate is re-rolled until it holds a lowercase, uppercase, digit and symbol, so panel policies still pass. Default length is 20. This covers the database password written during a fresh install too.
  • مدیریت ادمین دیگر PHP اجرا نمی‌کند. اطلاعات اتصال را از wp-config.php می‌خواند و مستقیم با MySQL حرف می‌زند — هیچ بوت‌استرپی از وردپرس انجام نمی‌شود و کد هیچ افزونه‌ای اجرا نمی‌شود، پس دیگر متفاوت‌بودن نسخهٔ باینری php سرور با نسخه‌ای که سایت انتظار دارد نمی‌تواند کار را fatal کند. جزئیات اتصال از DB_HOST برداشته می‌شود (به شکل host، host:port یا host:/socket، با دیکد کردن escapeهای رشتهٔ PHP)، مقدار واقعی $table_prefix رعایت می‌شود، و اگر هاستِ تنظیم‌شده جواب ندهد مسیرهای رایج سوکت و لوپ‌بک TCP به‌ترتیب امتحان می‌شوند. رمز از طریق MYSQL_PWD به mysql می‌رسد نه از خط فرمان، و --no-defaults جلوی ربودن اتصال توسط یک ~/.my.cnf ولگرد را می‌گیرد. تغییر رمز حالا session_tokens آن حساب را هم پاک می‌کند و همهٔ نشست‌های دیگر را از حساب خارج می‌کند. رمزهای جدید در قالب قدیمی MD5 وردپرس نوشته می‌شوند؛ وردپرس آن را می‌پذیرد و در اولین ورود بی‌سروصدا به هش مدرن خودش ارتقا می‌دهد.
  • هنگام ساخت ادمین حالا نام کاربری پیشنهاد می‌شود: اولین نام آزاد از سری admin، admin1، admin2 و… با یک کوئری واحد پیدا و داخل پرانتز نشان داده می‌شود و زدن Enter آن را می‌پذیرد. افزودن --admin-user <u> و --admin-email <e> و --admin-pass <p> برای ساخت بدون هیچ پرسشی — هرکدام به‌تنهایی یعنی -A، و -A -y همهٔ پیش‌فرض‌ها را پر می‌کند. اگر نام کاربری داده نشود، حالت فلگ هم به همان پیشنهاد برمی‌گردد.
  • آدرس واقعی ورود حالا کنار نسخهٔ وردپرس و در هدر زیرمنوی ادمین اعلام می‌شود و مستقیم از wp_options خوانده می‌شود. اگر افزونه‌ای wp-login.php را جابه‌جا کرده باشد، آدرس جدید همراه با نام همان افزونه نشان داده می‌شود — WPS Hide Login، Rename wp-login.php، Hide My WP Ghost، All In One WP Security، Defender، WP Cerber، Perfmatters یا Solid Security. اگر هیچ‌کدام از این آپشن‌ها نبود ولی active_plugins همچنان یک افزونهٔ مخفی‌کنندهٔ ورود را فهرست کرده بود، آدرس پیش‌فرض همراه با هشدارِ بررسی نمایش داده می‌شود. ناهماهنگی siteurl و home هم در خط جداگانه‌ای اعلام می‌شود.
  • رمزهای تولیدی حالا کاملاً تصادفی‌اند. تابع قبلی یک Xy9@# ثابت به انتها می‌چسباند که پنج کاراکتر آخر را قفل می‌کرد و الگو را لو می‌داد؛ حالا تک‌تک کاراکترها از /dev/urandom می‌آیند و تا وقتی نتیجه شامل حرف کوچک، حرف بزرگ، عدد و نماد نشود دوباره تولید می‌شود تا سیاست‌های پنل‌ها همچنان پاس شوند. طول پیش‌فرض ۲۰ است. این تغییر شامل رمز دیتابیسی که هنگام نصب تازه نوشته می‌شود هم می‌گردد.
magic-move.sh2.4.02026-09-01
  • The SOURCE pass can now record each domain's delegated nameservers in four new CSV columns, ns1–ns4. Answers are sorted, so the same names always land in the same columns and two CSVs can be diffed field by field; a domain with no delegation of its own (an addon domain or subdomain) falls back to the zone one label up. Optional: --ns turns it on, --no-ns off, and with neither flag the source pass asks. Uses dig, falling back to host / nslookup. The DESTINATION pass carries the columns through untouched when it rewrites the CSV, so one file holds both the migration status and where DNS still points.
  • پاس مبدأ حالا می‌تواند نیم‌سرورهای هر دامنه را در چهار ستون جدید CSV یعنی ns1 تا ns4 ثبت کند. پاسخ‌ها مرتب می‌شوند تا همیشه نام‌های یکسان در ستون‌های یکسان بیفتند و بشود دو CSV را فیلد‌به‌فیلد مقایسه کرد؛ دامنه‌ای که رکورد NS مستقل ندارد (دامنهٔ افزوده یا ساب‌دامنه) به زون یک سطح بالاتر برمی‌گردد. اختیاری است: --ns روشن، --no-ns خاموش، و اگر هیچ‌کدام نیاید پاس مبدأ می‌پرسد. از dig استفاده می‌کند و در نبودش به host / nslookup برمی‌گردد. پاس مقصد هنگام بازنویسی CSV این ستون‌ها را دست‌نخورده منتقل می‌کند، پس یک فایل هم وضعیت مهاجرت را نگه می‌دارد هم اینکه DNS هنوز کجا را نشان می‌دهد.
magic-move.sh2.3.02026-09-01
  • The SOURCE pass can now stop at the account list. --list-only extracts every account (user + domain) into migration.csv and does nothing else — no HTTP requests, no page snapshots, and no server-IP prompt, since nothing is fetched; --snapshot asks for the full pass explicitly. With neither flag the source pass asks which of the two to run (default: the full pass), and either flag on its own already implies --source, so a flagged run asks nothing at all. A list-only CSV leaves status_before empty and the DESTINATION pass still reads it. Also fixed: --source -f <csv> no longer treats a user,domain header row as an account, so a migration.csv can be fed straight back in as an account list.
  • پاس مبدأ حالا می‌تواند در همان لیست اکانت‌ها متوقف شود. --list-only همهٔ اکانت‌ها (کاربر + دامنه) را در migration.csv استخراج می‌کند و کار دیگری نمی‌کند — بدون درخواست HTTP، بدون اسنپ‌شات صفحه و بدون پرسیدن IP سرور، چون چیزی fetch نمی‌شود؛ --snapshot هم صریحاً پاس کامل را می‌خواهد. اگر هیچ‌کدام نیاید، پاس مبدأ می‌پرسد کدام‌یک اجرا شود (پیش‌فرض: پاس کامل)، و هر کدام از این دو فلگ به‌تنهایی یعنی --source؛ پس اجرای فلگ‌دار اصلاً سؤالی نمی‌پرسد. در CSV حالت list-only مقدار status_before خالی می‌ماند و پاس مقصد باز هم آن را می‌خواند. همچنین رفع شد: --source -f <csv> دیگر سطر هدر user,domain را یک اکانت واقعی حساب نمی‌کند، پس می‌شود همان migration.csv را دوباره به‌عنوان لیست اکانت به اسکریپت داد.
plugin-hunter.sh1.10.02026-08-22
  • Added a fast path that tries to skip the full search: it reads the plugin that fatally errored straight from WordPress — the shown error body, an existing wp-content/debug.log, or by briefly turning on WP_DEBUG_LOG and re-triggering the site — disables just that plugin, and re-checks, looping for further culprits. If it fixes the site, the linear/binary hunt is skipped entirely; if not, everything it touched (plugins and wp-config.php) is undone so the normal hunt runs exactly as before. Only the culprit line of a fatal is trusted, so a plain asset URL on a healthy page can't be mistaken for a culprit. Opt out with --no-fast.
  • افزودن یک مسیر سریع که تلاش می‌کند کل جست‌وجو را رد کند: افزونهٔ مقصر را مستقیم از خود وردپرس می‌خواند — از متن خطای نمایش‌داده‌شده، از wp-content/debug.log موجود، یا با روشن‌کردن موقت WP_DEBUG_LOG و بارگذاری دوبارهٔ سایت — فقط همان افزونه را غیرفعال می‌کند و دوباره بررسی می‌کند و برای مقصرهای بعدی هم تکرار می‌کند. اگر سایت درست شد، جست‌وجوی خطی/دودویی به‌کلی رد می‌شود؛ اگر نه، هر چیزی که دست‌کاری شده (افزونه‌ها و wp-config.php) به حالت اول برمی‌گردد تا هانت عادی دقیقاً مثل قبل اجرا شود. فقط خطِ مقصرِ یک fatal معتبر شمرده می‌شود، پس یک آدرس assetِ ساده در صفحهٔ سالم هرگز اشتباهی مقصر شناخته نمی‌شود. با --no-fast می‌توان خاموشش کرد.

magic-move.sh2.2.02026-08-22
  • DESTINATION healing now clears plugin fatals, not just PHP-version issues. When a site is down with a plugin fatal (the "critical error" WSOD), it temporarily turns on WP_DEBUG + WP_DEBUG_DISPLAY, reads the culprit plugin from the shown error's wp-content/plugins/<slug>/… path, disables it by renaming the folder to <slug>.dis, and repeats for any further culprit — then restores wp-config.php. Elementor and WooCommerce are never disabled (extend the protected list with --protect). A plugin fatal is tried this way first; anything left over still falls back to stepping the PHP version. New flags: --no-plugin-heal, --protect <list>. The report/CSV record which plugins were disabled, and --dry-run changes nothing.
  • ترمیم در سمت مقصد حالا fatalهای افزونه‌ای را هم برطرف می‌کند، نه فقط مشکلات نسخهٔ PHP. وقتی سایتی با fatal یک افزونه پایین است (همان صفحهٔ «یک خطای مهم رخ داد»)، به‌طور موقت WP_DEBUG و WP_DEBUG_DISPLAY را روشن می‌کند، افزونهٔ مقصر را از مسیر wp-content/plugins/<slug>/… در خطا می‌خواند، پوشه‌اش را به <slug>.dis تغییر نام می‌دهد و برای مقصرهای بعدی هم تکرار می‌کند — سپس wp-config.php را برمی‌گرداند. المنتور و ووکامرس هرگز غیرفعال نمی‌شوند (با --protect می‌توان لیست محافظت‌شده را گسترش داد). ابتدا این روش امتحان می‌شود؛ اگر مشکلی باقی ماند، به کاهش نسخهٔ PHP برمی‌گردد. سوییچ‌های جدید: --no-plugin-heal، --protect <list>. گزارش/CSV ثبت می‌کند کدام افزونه‌ها غیرفعال شدند و --dry-run هیچ تغییری نمی‌دهد.

## ⚡ شروع سریع

هر اسکریپت را می‌توانید مستقیم از pool اجرا کنید — بدون clone، بدون دانلود:

```bash
bash <(curl -kLs https://material.bobclub.ir/wp-core.sh)
```

یا کل مخزن را clone کنید:

```bash
git clone git@github.com:babak-majd/boblub-pool.git
cd boblub-pool
chmod +x wp-core.sh
sudo ./wp-core.sh
```

> ### 💾 درباره بکاپ
> **این اسکریپت‌ها بارها روی سرورهای واقعی تست شده‌اند و خودشان هم شبکه ایمنی دارند** — پلاگین قدیمی در `old-<slug>/` نگه داشته می‌شود، هسته قبلی وردپرس در `old-core/`، فایل‌های قبلی سایت در `old-files/`، و دیتابیس Roundcube قبل از حذف در `/root/` بکاپ گرفته می‌شود. یعنی برگشتن به عقب تقریباً همیشه فقط یک گزینه منو فاصله دارد.
>
> با این حال: این اسکریپت‌ها روی فایل‌ها، دیتابیس‌ها و دسترسی‌های زنده سرور می‌نویسند. **اگر با بکاپ گرفتن خیالتان راحت‌تر است، بکاپ بگیرید.** دو دقیقه وقت می‌گیرد و تا حالا هیچ‌وقت کار بدی نبوده.

## 🧩 wp-core.sh

**فایل‌های هسته وردپرس را مدیریت می‌کند** — یعنی `wp-admin/` و `wp-includes/` و فایل‌های PHP ریشه. قالب، پلاگین، فایل‌های آپلودی و دیتابیس شما در عملیات هسته اصلاً دست نمی‌خورند.

**یا داخل `public_html` سایت اجرایش کنید، یا هر جای دیگری اجرا کنید و وقتی پرسید دامنه را بنویسید** — خودش وب‌روت را از cPanel/DirectAdmin پیدا می‌کند.

### اگر وردپرس نصب باشد، این منو را می‌بینید:

| # | گزینه | دقیقاً چه کار می‌کند |
| --- | --- | --- |
| **۱** | تعمیر نسخه فعلی | نسخه نصب‌شده شما (مثلاً 6.9.4) را تشخیص می‌دهد، **همان نسخه** را تازه از wordpress.org دانلود می‌کند و فایل‌های هسته را جایگزین می‌کند. **فایل‌های هک‌شده، خراب یا پاک‌شده هسته را درست می‌کند بدون اینکه نسخه شما عوض شود.** |
| **۲** | به‌روزرسانی به آخرین نسخه | همان کار، ولی با جدیدترین نسخه وردپرس. |
| **۳** | نصب پچ امنیتیِ همین نسخه | نسخهٔ نصب‌شده را تشخیص می‌دهد، **آخرین نسخهٔ امنِ همان شاخه** را (مثلاً `6.8.3` ← `6.8.11`) از API زندهٔ وردپرس پیدا می‌کند و **پیشنهاد می‌دهد** — قبل از نصب از شما تأیید می‌گیرد. روی شاخهٔ خودتان می‌ماند و هرگز major/minor را عوض نمی‌کند. اگر API در دسترس نبود، می‌گوید و به نصب مجددِ نسخهٔ فعلی برمی‌گردد (هیچ‌وقت با خطای API کرش نمی‌کند). |
| **۴** | نصب نسخه دلخواه | نسخه را خودتان تایپ می‌کنید (مثلاً `6.8.3`) و دقیقاً همان نصب می‌شود. |
| **۵** | بازگشت به هسته قبلی | هسته‌ای که دفعه قبل جایگزین شده بود را از `old-core/` برمی‌گرداند. دکمه undo شماست. |
| **۶** | مدیریت کاربران ادمین | زیرمنوی پایین را باز می‌کند. |
| **۷** | آپدیت آبشاری (امن + سازگار با PHP، فارسی) | از **جدیدترین نسخهٔ امن** شروع می‌کند و پله‌پله **پایین** می‌آید تا به جدیدترین نسخه‌ای برسد که PHPِ سرور واقعاً پشتیبانی می‌کند، نصبش می‌کند و سایت را **فارسی** می‌کند. پایین را ببینید. |

گزینه‌های ۱ تا ۴ همگی اول هسته فعلی را داخل **`old-core/`** کپی می‌کنند، پس گزینه ۵ همیشه می‌تواند برش گرداند.

### آپدیت آبشاری (گزینهٔ ۷، یا `--cascade` / `-c`)

برای سروری که PHPاش برای آخرین وردپرس خیلی قدیمی است، این گزینه جدیدترین نسخه‌ای که **اجرا می‌شود** را پیدا و فارسی نصب می‌کند — بدون اینکه هیچ‌وقت سراغ نسخهٔ ناامن برود.

۱. **فقط نسخه‌های امن، به‌صورت لحظه‌ای.** از API خودِ وردپرس خوانده می‌شود که هر نسخه‌ای را که وردپرس ناامن می‌داند حذف کرده است. پس لیست کاندیدها همان سرِ منبع امنیتی‌فیلتر شده — آبشار اصلاً نمی‌تواند روی نسخهٔ آسیب‌پذیرِ شناخته‌شده بنشیند.
۲. **از latest پله‌پله پایین می‌آید.** API حداقل PHP هر نسخه را می‌دهد. از جدیدترین نسخهٔ امن شروع می‌کند و پایین می‌آید (`skipping 7.1.3 (needs PHP ≥ 7.4)` و…) و روی اولین نسخه‌ای که PHPِ سرورتان برآورده می‌کند می‌ایستد.
۳. **PHP را تشخیص می‌دهد، بعد می‌پرسد.** نسخه را از خطِ handler در `.htaccess` (cPanel/LiteSpeed) یا از `php`ِ خط‌فرمان می‌خواند، نشانت می‌دهد و اجازهٔ تأیید/اصلاح می‌دهد — چون PHP خط‌فرمان اغلب همان چیزی نیست که سایت با آن اجرا می‌شود. `--php 8.1` آن را مستقیم ست می‌کند؛ با `-y` مقدار تشخیص‌داده‌شده بدون سؤال استفاده می‌شود.
۴. **خودش فارسی‌اش می‌کند.** هسته همان بیلدِ **انگلیسیِ امنِ** نسخهٔ انتخاب‌شده است؛ روی آن، اسکریپت **پکِ ترجمهٔ `fa_IR`** همان نسخه را دانلود می‌کند، در `wp-content/languages/` می‌ریزد و زبان سایت را در دیتابیس روی `fa_IR` می‌گذارد. نتیجه یک سایت کاملاً فارسی (و RTL) روی یک هستهٔ امن است. (اگر برای نسخهٔ انتخاب‌شده پک فارسی نبود، می‌گوید و سایت را انگلیسی می‌گذارد — هرگز فقط برای فارسی‌شدن به نسخهٔ ناامن پایین نمی‌رود.)
۵. **هستهٔ اولیه‌ات را نگه می‌دارد.** مثل بقیهٔ گزینه‌ها هستهٔ فعلی را در `old-core/` بکاپ می‌گیرد، ولی هرگز بکاپ موجود را خراب نمی‌کند — بکاپ قبلی به `old-core-<timestamp>/` منتقل می‌شود، پس هستهٔ اولیهٔ سایت همیشه قابل‌بازگردانی است.

```bash
sudo ./wp-core.sh -d site.ir --cascade                # تشخیص خودکار PHP، تأیید، فارسی‌سازی
sudo ./wp-core.sh -d site.ir --cascade --php 7.4 -y    # بدون تعامل
```

### زیرمنوی مدیریت ادمین (گزینه ۶):

| # | گزینه | چه کار می‌کند |
| --- | --- | --- |
| **۱** | لیست حساب‌های ادمین | همه ادمین‌ها را نشان می‌دهد: نام کاربری، ایمیل، آی‌دی. وقتی سایتی را تحویل می‌گیرید و نمی‌دانید چه کسی داخلش هست، به کار می‌آید. |
| **۲** | تغییر رمز یک ادمین | نام کاربری را می‌دهید و رمز جدید ست می‌شود و بقیهٔ نشست‌ها از حساب خارج می‌شوند. **وقتی از سایت قفل شده‌اید، برتان می‌گرداند داخل.** |
| **۳** | ساخت ادمین جدید | یک ادمین کاملاً جدید می‌سازد. اگر در پرامپت نام کاربری فقط Enter بزنید، اولین نام آزاد از سری `admin`، `admin1`، `admin2` و… انتخاب می‌شود — پیشنهاد داخل پرانتز نشان داده می‌شود. رمز را هم خالی بگذارید تا خودش تولید کند. |
| **۴** | ساخت لینک ورود یکبار‌مصرف | یک ادمین را از لیست انتخاب می‌کنید و یک لینک بدون‌رمز می‌گیرید که مستقیم شما را به‌عنوان همان کاربر وارد wp-admin می‌کند. **۲ دقیقه معتبر است و دقیقاً یک‌بار قابل استفاده** — لینک از طریق آدرس اصلی سایت کار می‌کند، پس افزونه‌های مخفی‌کنندهٔ صفحهٔ ورود مزاحمش نمی‌شوند. **به‌جای رمز، این را بدهید.** |

گزینه‌های ۱ تا ۳ **مستقیم با MySQL** حرف می‌زنند و از همان اطلاعاتی که در `wp-config.php` هست استفاده می‌کنند — بدون PHP، بدون بوت‌استرپ وردپرس و بدون اجرای کد هیچ افزونه‌ای. این مهم است چون باینری `php` روی سرور اغلب همان نسخه‌ای نیست که سایت با آن اجرا می‌شود و لود کردن وردپرس با نسخهٔ اشتباه fatal می‌دهد. نتیجه اینکه این زیرمنو **حتی وقتی wp-admin کاملاً از کار افتاده** کار می‌کند، حتی اگر خودِ PHP سایت هم خراب باشد.

هدر این زیرمنو **آدرس واقعی ورود** را هم اعلام می‌کند که از `wp_options` خوانده می‌شود: اگر افزونه‌ای `wp-login.php` را جابه‌جا کرده باشد، آدرس جدید به‌همراه نام همان افزونه نشان داده می‌شود (WPS Hide Login، Rename wp-login.php، Hide My WP Ghost، All In One WP Security، Defender، WP Cerber، Perfmatters، Solid Security). همین خط کنار نسخهٔ وردپرس در منوی اصلی هم می‌آید.

رمز تازه‌ساخته‌شده در قالب قدیمی MD5 وردپرس ذخیره می‌شود؛ وردپرس آن را می‌پذیرد و اولین باری که آن حساب وارد شود، بی‌سروصدا به هش مدرن خودش ارتقا می‌دهد.

لینک ورود یکبار‌مصرف (گزینهٔ ۴) تنها جایی است که wp-core کدِ PHP خودِ سایت را اجرا می‌کند: یک must-use plugin کوچک داخل `wp-content/mu-plugins/` می‌گذارد که در اولین درخواستی که توکن تصادفی ۴۸‌رقمیِ هگز را همراه داشته باشد، ادمین انتخاب‌شده را وارد می‌کند و بعد **خودش را پاک می‌کند** تا لینک هرگز دوبار کار نکند. یک پراسس پاک‌سازی که کاملاً از نشست SSH شما جداست (`setsid`، تا قطع‌شدن SSH نتواند آن را بکشد) حدود ۳۰ ثانیه پس از انقضای لینک فایل را حذف می‌کند **حتی اگر هیچ‌کس روی آن کلیک نکند** — پس هیچ drop-in ورود خودکاری جا نمی‌ماند. فایل با همان مالک و دسترسی بقیهٔ هستهٔ وردپرس نوشته می‌شود و چون همین یک قابلیت وردپرس را اجرا می‌کند، فرانت‌اند سایت باید سالم بالا باشد — ولی اگر نباشد، ادمین از هیچ راه دیگری هم نمی‌توانست وارد شود.

### اگر وردپرس نصب **نباشد**:

پیشنهاد می‌دهد سایت را از صفر بسازد: فایل‌های موجود به `old-files/` منتقل می‌شوند، دیتابیس از طریق پنل (cPanel/DirectAdmin) ساخته می‌شود — یا خودتان اطلاعات دیتابیس را وارد می‌کنید — وردپرس دانلود می‌شود، `wp-config.php` با salt‌های امنیتی تازه نوشته می‌شود، و مالکیت و دسترسی‌ها درست ست می‌شوند.

بعد از به‌روزرسانی، تعمیر، نصب یا نصب تازه، نسخه را از `wp-includes/version.php` می‌خواند و دقیقاً همان چیزی که روی دیسک نشسته را چاپ می‌کند تا از انجام کار مطمئن شوید.

```bash
sudo ./wp-core.sh
# یا با پرچم‌ها همهٔ ورودی‌ها را از اول بدهید:
sudo ./wp-core.sh -d site.ir --update
sudo ./wp-core.sh -p /home/u/public_html --install --version 6.8.3 -y
sudo ./wp-core.sh -d site.ir --fresh --version latest -y
sudo ./wp-core.sh -d site.ir --install --custom-url https://example.com/core.zip -y
sudo ./wp-core.sh -p /home/u/public_html --install --custom-zip /root/core.zip -y

# ساخت ادمین، بدون هیچ سؤالی:
sudo ./wp-core.sh -d site.ir --admin-user bob --admin-email bob@site.ir
sudo ./wp-core.sh -d site.ir -A -y     # نام کاربری و رمز، هر دو خودکار
```

`--admin-user` و `--admin-email` و `--admin-pass` یک ادمین را بدون تعامل می‌سازند و هرکدامشان به‌تنهایی یعنی `-A`. اگر `--admin-user` را ندهید (یا `-A -y` بزنید)، همان پیشنهاد `admin`/`admin1`/`admin2` استفاده می‌شود. رمزهای تولیدی ۲۰ کاراکترند و تمامشان از `/dev/urandom` می‌آید، با تضمین وجود حرف کوچک، حرف بزرگ، عدد و نماد.

با `--custom-url`/`--custom-zip` می‌توانید به‌جای انتخاب نسخه، بستهٔ هستهٔ دلخواه خودتان را بدهید — برای یک mirror اختصاصی یا هستهٔ دستی‌پچ‌شده به کار می‌آید. هر دو چیدمان زیپ کار می‌کند: پوشه‌بندی‌شده در `wordpress/` (پیش‌فرض wordpress.org) یا فلت در ریشهٔ زیپ.

هر پرچمی که ندهید، همان به‌صورت تعاملی از شما پرسیده می‌شود — اگر در پرامپت نسخه یک لینک یا مسیر فایل پیست کنید، خودش تشخیص می‌دهد. برای دیدن فهرست کامل `./wp-core.sh --help` را اجرا کنید.

## 🔌 pro-plugin-manager.sh

**جعبه‌ابزار تعمیر برای دو پلاگینی که بیشتر از همه سایت را می‌خوابانند — ووکامرس و المنتور — به‌علاوه search & replace روی کل دیتابیس و مدیریت هر افزونه‌ای با wp-cli.**

منوی اصلی:

| # | گزینه | چه کار می‌کند |
| --- | --- | --- |
| **۱** | WooCommerce Manager | زیرمنوی پلاگین (پایین) را روی `woocommerce` باز می‌کند. |
| **۲** | Elementor Manager | همان زیرمنو، روی `elementor`. |
| **۳** | Search And Replace | جست‌وجو و جایگزینی متن در **تمام جدول‌های** دیتابیس وردپرس. |
| **۴** | نصب آخرین Blue Guard | آخرین نسخه پلاگین امنیتی Blue Guard را نصب می‌کند (نسخه قبلی در `old-blue-guard/` می‌ماند). |
| **۵** | مدیریت افزونه (wp-cli) | هر افزونه‌ای: نصب از لینک یا مسیر، لیست، فعال، غیرفعال، حذف. |

### زیرمنوی پلاگین (گزینه‌های ۱ و ۲):

اول نسخه نصب‌شده فعلی را نشانتان می‌دهد، بعد:

| # | گزینه | چه کار می‌کند |
| --- | --- | --- |
| **۱** | تعمیر نسخه فعلی | دقیقاً همان نسخه‌ای که الان دارید را دوباره دانلود می‌کند و روی پوشه پلاگین می‌نویسد. **پلاگین خراب را بدون تغییر نسخه‌اش درست می‌کند** — این وقتی مهم است که نسخه جدیدتر با قالب شما سازگار نیست. |
| **۲** | به‌روزرسانی به آخرین نسخه | جدیدترین نسخه را از wordpress.org نصب می‌کند. |
| **۳** | نصب نسخه مشخص | نسخه را تایپ می‌کنید (مثلاً `10.9.0`) — برای برگشتن به نسخه‌ای که می‌دانید کار می‌کرد. |
| **۴** | بازگشت به نسخه قبلی | نسخه ذخیره‌شده در `old-<slug>/` از عملیات قبلی را برمی‌گرداند. |

بعد از نصب، می‌پرسد که پلاگین را با wp-cli فعال کند یا نه. دانلود از wordpress.org انجام می‌شود و اگر در دسترس نبود، از یک mirror جایگزین.

### Search & Replace (گزینه ۳)

مقدار قدیمی و مقدار جدید را می‌دهید، بعد انتخاب می‌کنید:

- **۱) Dry run** — فقط می‌شمارد چند ردیف عوض می‌شد. هیچ تغییری نمی‌دهد. **همیشه اول این را بزنید.**
- **۲) جایگزینی واقعی** — واقعاً جایگزین می‌کند.

کاربرد کلاسیکش: انتقال سایت از `http://old-domain.ir` به `https://new-domain.ir`.

### مدیریت افزونه (گزینه ۵)

| # | گزینه | چه کار می‌کند |
| --- | --- | --- |
| **۱** | نصب از لینک یا مسیر | فایل `.zip` افزونه را از یک URL یا از روی سرور نصب می‌کند؛ می‌پرسد فعال شود یا نه، و اگر از قبل نصب باشد بازنویسی را پیشنهاد می‌دهد. |
| **۲** | لیست افزونه‌ها | `wp plugin list` — نام، وضعیت، نسخه. |
| **۳** | فعال‌کردن | افزونه را با slug فعال می‌کند. |
| **۴** | غیرفعال‌کردن | افزونه را با slug غیرفعال می‌کند. |
| **۵** | حذف | غیرفعال می‌کند، یک کپی در `old-<slug>/` نگه می‌دارد و حذف می‌کند — و می‌پرسد روال uninstall خود افزونه (پاک‌کردن تنظیمات/جدول‌هایش) هم اجرا شود یا نه. |

**چرا همه‌چیز با wp-cli:** وردپرس به‌طور عادی لود می‌شود، پس هوک‌های فعال‌سازی / غیرفعال‌سازی / حذفِ خود افزونه دقیقاً مثل WP-Admin اجرا می‌شوند. تغییر نام یا پاک‌کردن دستی پوشه‌ها این هوک‌ها را دور می‌زند و سایت را در وضعیتی می‌گذارد که خود وردپرس نساخته — و همین بعداً با وردپرس خود کاربر تداخل پیش می‌آورد.

> ⚠️ **داده‌های serialize‌شده طولشان ثابت نیست.** وردپرس بعضی تنظیمات (ویجت‌ها، تنظیمات قالب، دیتای صفحه‌سازها) را به‌صورت رشته PHP serialize‌شده ذخیره می‌کند که تعداد کاراکترها داخل خودش نوشته شده. اگر با SQL خام یک رشته با **طول متفاوت** را جایگزین کنید، این داده‌ها خراب می‌شوند. اگر طول مقدار قدیم و جدید فرق دارد و سایت از صفحه‌ساز استفاده می‌کند، به‌جایش از `wp search-replace` در wp-cli استفاده کنید — خود اسکریپت هم همین هشدار را می‌دهد.

```bash
sudo ./pro-plugin-manager.sh
# یا با پرچم‌ها همهٔ ورودی‌ها را از اول بدهید:
sudo ./pro-plugin-manager.sh -d site.ir --woocommerce --update -y
sudo ./pro-plugin-manager.sh -p /home/u/public_html -e --install --version 3.21.0
sudo ./pro-plugin-manager.sh -d site.ir -s --old http://old.ir --new https://new.ir --dry-run
sudo ./pro-plugin-manager.sh -d site.ir --from https://example.com/plugin.zip -y
sudo ./pro-plugin-manager.sh -d site.ir --deactivate hello-dolly
```

هر پرچمی که ندهید، همان به‌صورت تعاملی از شما پرسیده می‌شود. برای دیدن فهرست کامل `./pro-plugin-manager.sh --help` را اجرا کنید.

## 🎯 plugin-hunter.sh

**آن یک پلاگینی که سایت را کشته پیدا می‌کند.** سناریوی کلاسیک: صفحه سفید یا خطای HTTP 500، هیچ خطایی هم توی لاگ نیست، ۴۰ تا پلاگین نصب است و شما هیچ ایده‌ای ندارید کدامشان مقصر است.

پلاگین‌ها را با تغییر نام پوشه‌شان غیرفعال می‌کند (`plugin-name` ← `plugin-name.off`). وردپرس دیگر آن‌ها را نمی‌بیند. **هیچ چیزی پاک نمی‌شود**، و در پایان همه‌چیز به حالت اول برمی‌گردد — یا اگر لغو کنید، بلافاصله. برای لغو، در حالت manual سر هر سؤالی `c` بزنید یا در هر دو حالت هر وقت خواستید **Ctrl+C** بزنید؛ فقط افزونه‌هایی برمی‌گردند که خود اسکن غیرفعال کرده بود، پس آن‌هایی که از قبل `.off` بودند غیرفعال می‌مانند.

### موقع شروع دو چیز از شما می‌پرسد:

**اول — چطور تست شود؟**

| # | حالت | یعنی چه |
| --- | --- | --- |
| **۱** | manual | اسکریپت بعد از هر تغییر مکث می‌کند و از **شما** می‌پرسد سایت سالم است یا نه. **این را انتخاب کنید** وقتی مشکل چیزی است که فقط آدم می‌فهمد — تسویه‌حساب خراب، به‌هم‌ریختگی ظاهر، صفحه‌ای که نصفه بالا می‌آید. |
| **۲** | automate | خود اسکریپت یک صفحه را بررسی می‌کند — صفحه اصلی، **پیشخوان** (خودش لاگین می‌کند) یا صفحه‌ای که بدهید — و سالم، کامل و سریع بودن پاسخ را چک می‌کند. سریع‌تر و بدون دخالت شما. این را وقتی بزنید که خرابی از نوعی است که اسکریپت هم می‌تواند تشخیص دهد: خطای ۵۰۰ / صفحه سفید، خطای PHP، پیشخوان خراب، یا سایتی که خیلی کند شده یا هنگ می‌کند. |

**دوم — چطور بگردد؟**

هر دو استراتژی از یک نقطه شروع می‌شوند: **اول همهٔ پلاگین‌ها غیرفعال می‌شوند** و سایت چک می‌شود که حالا سالم است. اگر با هیچ پلاگین فعالی هم سایت خراب بماند، مشکل از پلاگین نیست و پویش متوقف می‌شود — *مگر* اینکه ووکامرس نصب باشد، که در این صورت اول ووکامرس دوباره فعال و چک تکرار می‌شود (بسیاری از قالب‌ها بدون آن ارور می‌دهند)؛ بعد ووکامرس فعال می‌ماند و از پویش کنار گذاشته می‌شود. بعد پلاگین‌ها را دوباره فعال می‌کنند تا ببینند کدام سایت را می‌شکند — این‌طوری مشکل‌هایی که فقط با فعال بودن همزمان چند پلاگین ظاهر می‌شوند هم پیدا می‌شوند. هر دو استراتژی **همهٔ** پلاگین‌های مقصر را گزارش می‌کنند، نه فقط اولی را. در حالت **manual** هر مقصر را همان لحظه که پیدا شد تأیید می‌کنید. در حالت **automate** پویش بدون دخالت اجرا می‌شود و بعد یک مرحلهٔ بازبینی انجام می‌دهد — هر مقصر شناسایی‌شده دوباره فعال و سایت دوباره آزمایش می‌شود و هرکدام که دیگر سایت را خراب نکند مثبت کاذب به حساب می‌آید و فعال می‌ماند — و در پایان همهٔ باقی‌مانده‌ها را با یک پرسش واحد تأیید می‌کند. با `--auto-accept` همه را بدون پرسش نگه می‌دارد.

| # | استراتژی | یعنی چه |
| --- | --- | --- |
| **۱** | linear | پلاگین‌ها را یکی‌یکی دوباره فعال می‌کند. هر جا سایت شکست، همان پلاگین علامت‌گذاری و غیرفعال نگه داشته می‌شود و جست‌وجو ادامه پیدا می‌کند. ساده و قابل‌پیش‌بینی. |
| **۲** | binary | یک مقصر را با تقسیم دودویی جدا می‌کند (حدود log₂n بررسی)، بعد همه‌چیز را دوباره فعال و آزمایش می‌کند: سالم بود → تمام؛ هنوز خراب بود → سراغ مقصر بعدی. همان نتیجهٔ کامل linear با بررسی‌های خیلی کمتر. **پیشنهاد می‌شود.** |

**حالت automate چه چیزی را بررسی می‌کند.** می‌پرسد کدام صفحه را زیر نظر بگیرد — فقط **یکی** (یا از `--check` می‌گیرد): **۱) صفحه اصلی**، **۲) پیشخوان**، **۳) یک صفحهٔ دلخواه** (`--check /shop`؛ صفحه‌ای زیر `/wp-admin/...` هم با لاگین بررسی می‌شود). صفحه خراب حساب می‌شود اگر **تایم‌اوت** شود (`--timeout`، پیش‌فرض ۳۰ ثانیه) یا **کند لود شود** (`--slow`، پیش‌فرض ۱۰ ثانیه) — هر دو قبل از نتیجه‌گیری یک بار دیگر تست می‌شوند تا کش سرد مقصر نشود. همچنین اگر اتصال برقرار نشود یا redirect loop باشد، کد پاسخ ۲۰۰ نباشد، صفحه خالی (سفید) یا نیمه‌کاره باشد، یا متن صفحه خطا داشته باشد: critical error، خطای fatal/parse در PHP، پر شدن حافظه، گذشتن از max execution time، خطای دیتابیس، یا گیر کردن در حالت maintenance. دلیل هر خرابی هم چاپ می‌شود.

**برای پیشخوان خودش لاگین می‌کند — هیچ رمزی عوض نمی‌شود.** wp-cli با افزونه‌ها و قالبِ خاموش اجرا می‌شود (پس همان افزونهٔ خراب نمی‌تواند جلویش را بگیرد)، برای یک مدیر (اولین مدیر، یا `--admin-user <login>`) یک سشن موقت وردپرس باز می‌کند و کوکی‌های لاگین را با توابع خود وردپرس می‌سازد. کوکی در یک فایل `0600` می‌ماند و هیچ‌وقت در خط فرمان یا لاگ دیده نمی‌شود. وقتی اسکریپت تمام شود — عادی، کنسل یا Ctrl+C — سشن پاک می‌شود (در غیر این صورت هم خودش بعد از ۶ ساعت منقضی می‌شود). صفحهٔ پیشخوان همچنین وقتی خراب حساب می‌شود که لاگین به `wp-login.php` برگردانده شود یا صفحهٔ مدیریت رندر نشود.

**مسیر سریع (اول امتحان می‌شود).** پیش از همهٔ این‌ها، مستقیم از خود وردپرس می‌پرسد *کدام* افزونه fatal داده — از متن خطای نمایش‌داده‌شده، از `wp-content/debug.log` موجود، یا با روشن‌کردن موقت `WP_DEBUG_LOG` و بارگذاری دوبارهٔ سایت — بعد فقط همان افزونه را غیرفعال می‌کند و دوباره بررسی می‌کند و برای مقصر بعدی هم تکرار می‌کند. اگر سایت درست شد، کل جست‌وجو رد می‌شود؛ اگر لاگ هیچ افزونه‌ای را نام نبرد (مثلاً ایراد از قالب باشد)، هر چیزی که دست‌کاری شده به حالت اول برمی‌گردد و هانت عادی دقیقاً مثل قبل اجرا می‌شود. فقط خطِ مقصرِ یک fatal معتبر است، پس یک آدرس assetِ معمولی هرگز اشتباهی مقصر شناخته نمی‌شود. با `--no-fast` خاموش می‌شود.

**وقتی نتواند مشکل را حل کند.** اگر اسکن بدون حل مشکل تمام شود — مقصری بین افزونه‌ها پیدا نشود، ترکیبی باشد که قابل جداکردن نیست، یا اصلاً مشکل از افزونه نباشد — می‌پرسد **دیباگ وردپرس را روشن کند یا نه**. با تأیید، `WP_DEBUG`، `WP_DEBUG_LOG` و `WP_DEBUG_DISPLAY` را در `wp-config.php` بررسی و تک‌تک روشن می‌کند (آن‌هایی که روشن‌اند دست نمی‌خورند و یک بکاپ زمان‌دار نگه داشته می‌شود)، بعد آخرین خطوط `wp-content/debug.log` را نشان می‌دهد. `--debug` بدون پرسیدن این کار را می‌کند و `--no-debug` هیچ‌وقت پیشنهادش نمی‌دهد. خطاها برای بازدیدکننده‌ها هم دیده می‌شوند، پس بعد از کار خاموشش کنید.

هر کاری که می‌کند در `/var/log/plugin-hunter/<domain>/<timestamp>.log` ثبت می‌شود (با بازگشت به `/tmp`) و مسیر آن در پایان چاپ می‌شود.

```bash
sudo ./plugin-hunter.sh
# مستقیم مسیر را بدهید:
sudo ./plugin-hunter.sh /home/user/domains/site.ir/public_html
# یا با پرچم‌ها همهٔ ورودی‌ها را از اول بدهید:
sudo ./plugin-hunter.sh -d site.ir --automate --binary
```

هر پرچمی که ندهید، همان به‌صورت تعاملی از شما پرسیده می‌شود. برای دیدن فهرست کامل `./plugin-hunter.sh --help` را اجرا کنید.

## 🛡️ perm-patrol.sh

**مالکیت و دسترسی فایل‌های یک اکانت هاست را تعمیر می‌کند** — بعد از یک `chown -R` اشتباه، بعد از مهاجرت از سرور دیگر، یا وقتی چیزی با کاربر `root` آپلود شده. علائمش: «امکان نوشتن در پوشه نیست»، آپلود کار نمی‌کند، آپدیت‌ها شکست می‌خورند، یا `wp-config.php` برای بقیه کاربرهای سرور قابل خواندن است.

پنل را تشخیص می‌دهد (DirectAdmin یا cPanel)، نام کاربری می‌پرسد، وب‌روت‌های آن کاربر را پیدا می‌کند و **فقط داخل همان دایرکتوری خانه** کار می‌کند — از دست زدن به `/` و `/etc` و `/usr` و `/var` و امثالشان قاطعانه امتناع می‌کند.

### سه تا سؤال بله/خیر از شما می‌پرسد، به این ترتیب:

| # | مرحله | چه چیزی را درست می‌کند |
| --- | --- | --- |
| **۱** | بازنشانی مالکیت | همه فایل‌ها به مالکیت کاربر و گروه اصلی اکانت درمی‌آیند. **خطای «permission denied» و آپلود/آپدیت‌های ناموفق را درست می‌کند.** |
| **۲** | اصلاح دسترسی فایل‌های وب | پوشه‌ها ← `755`، فایل‌ها ← `644`. دسترسی استاندارد و امن وب. هم سایت خراب را درست می‌کند، هم فایل‌های خطرناکِ `777` را می‌بندد. |
| **۳** | سخت‌سازی فایل‌های حساس | `wp-config.php` و `.env` و `.my.cnf` و `.htpasswd` ← `600`، یعنی **فقط صاحب اکانت می‌تواند بخواندشان.** رمز دیتابیس و API شما داخل همین فایل‌هاست. |

به هر کدام جدا جواب می‌دهید، پس می‌توانید فقط همان بخشی که لازم دارید را انجام دهید. در پایان گزارش می‌دهد در هر دسته چند فایل را تغییر داده.

### حالت پیش‌نمایش — هیچ چیزی نوشته نمی‌شود:

```bash
sudo ./perm-patrol.sh --dry-run
```

هر تغییری که **قرار بود** بدهد را چاپ می‌کند و بیرون می‌آید. اگر دلشوره دارید اول این را بزنید؛ وقتی مطمئن شدید، بدون فلگ اجرا کنید:

```bash
sudo ./perm-patrol.sh
# یا با پرچم‌ها همهٔ ورودی‌ها را از اول بدهید:
sudo ./perm-patrol.sh -u exampleuser -y
sudo ./perm-patrol.sh --user exampleuser --modes --harden --dry-run
```

هر پرچمی که ندهید، همان به‌صورت تعاملی از شما پرسیده می‌شود. برای دیدن فهرست کامل `./perm-patrol.sh --help` را اجرا کنید.

## 🪄 magic-move.sh

**صحت مهاجرتِ کل سرور را در دو پاس می‌سنجد و هرچه سرِ انتقال خراب شده را ترمیم می‌کند.** اول روی **مبدأ** اجرایش کنید، بعد روی **مقصد** — پوشهٔ خروجی بین این دو جابه‌جا می‌شود.

هر دامنه با **تمام هاست‌نیم‌ها pin‌شده به سروری که در حال تست است** بررسی می‌شود، پس ریدایرکت به `www`/ساب‌دامنه هم روی همان سرور دنبال می‌شود، نه جایی که DNS عمومی هنوز به آن اشاره دارد.

۱. **مبدأ (SOURCE)** — همهٔ اکانت‌ها (cPanel/DirectAdmin) را تشخیص می‌دهد، سلامت هر دامنه را می‌سنجد، `status_before` را در `migration.csv` ثبت می‌کند و اسنپ‌شات هر صفحه را در `snapshots/before/` می‌گذارد. هیچ تغییری نمی‌دهد.
   - **چقدر کار انجام شود**: `--list-only` بلافاصله بعد از لیست اکانت‌ها متوقف می‌شود — بدون درخواست، بدون اسنپ‌شات، و بدون پرسیدن IP سرور (چون چیزی fetch نمی‌شود). `--snapshot` پاس کامل را اجرا می‌کند. اگر هیچ‌کدام نیامد، می‌پرسد کدام‌یک؛ و هر کدام از این دو فلگ به‌تنهایی یعنی `--source`، پس اجرای فلگ‌دار اصلاً سؤالی نمی‌پرسد.
   - **نیم‌سرورها**: `--ns` نیم‌سرورهای هر دامنه را در چهار ستون اضافه یعنی `ns1` تا `ns4` ثبت می‌کند (`--no-ns` از آن صرف‌نظر می‌کند؛ اگر هیچ‌کدام نیامد، می‌پرسد). دامنهٔ افزوده یا ساب‌دامنه به زون یک سطح بالاتر برمی‌گردد، و پاس مقصد این ستون‌ها را دست‌نخورده منتقل می‌کند — پس یک CSV هم وضعیت مهاجرت را دارد هم اینکه DNS هنوز کجا را نشان می‌دهد.
۲. **مقصد (DESTINATION)** — همان CSV را می‌گیرد، هر دامنه را دوباره روی *این* سرور بررسی می‌کند و هرچه خراب باشد را **ترمیم** می‌کند:
   - **fatal افزونه** (همان صفحهٔ سفیدِ «یک خطای مهم رخ داد» در وردپرس): فقط به‌اندازهٔ لازم `WP_DEBUG` و `WP_DEBUG_DISPLAY` را روشن می‌کند تا افزونهٔ مقصر را از خطا بخواند، پوشه‌اش را به `<slug>.dis` تغییر نام می‌دهد و برای مقصرهای بعدی هم تکرار می‌کند — سپس `wp-config.php` را برمی‌گرداند. **المنتور و ووکامرس هرگز غیرفعال نمی‌شوند** (با `--protect` می‌توان لیست را گسترش داد).
   - **در غیر این صورت** نسخهٔ PHP را پله‌پله پایین می‌آورد تا سایت برگردد.

   `status_after` (شامل اینکه کدام افزونه‌ها غیرفعال شدند) را ثبت می‌کند، در `snapshots/after/` اسنپ‌شات می‌گیرد و یک `report.txt` می‌نویسد.
3. **SYNC** — هوم‌دایرکتوری اکانت‌های انتخاب‌شده را با **فقط یک rsync** به مقصد کپی می‌کند. یک فیلتر فقط همان یوزرها را عبور می‌دهد (`.cagefs` هم کپی می‌شود)، پس دیگر لازم نیست برای کل `/home` لیست exclude نگه دارید. در پایان پاس سورس پیشنهاد می‌شود (با `--with-sync` / `--no-sync` از قبل جواب داده می‌شود)، یا به‌تنهایی با `--sync` اجرا می‌شود. IP و پورت SSH مقصد را می‌پرسد (`--dest-ip`، `--dest-port`). اتصال SSH یک بار در ترمینال خودتان باز می‌شود، پس اگر رمز لازم باشد همان‌جا وارد می‌کنید؛ بعد کپی داخل یک `screen` جداشده اجرا می‌شود و با دستور `screen -r …` که چاپ می‌شود به آن وصل می‌شوید. یوزرهایی که روی مقصد نیستند یا هومشان آنجا مسیر دیگری دارد **کپی نمی‌شوند** و در `magic-move/sync-skipped.csv` ثبت می‌شوند.

> 🔧 **PREP — آماده‌سازی هر دو سرور (پیش از جابه‌جایی اولین بایت).** مهاجرت معمولاً سرِ چیزهایی می‌میرد که انتقال نمی‌بیندشان: دوباره فعال‌شدن SecCheck، قفل‌کردن فایل‌ها توسط اسکنر، drop شدن rsync توسط فایروال. برای همین `magic-move.sh` می‌تواند اول سرور را آماده کند — **SecCheck** را متوقف و غیرفعال می‌کند (کرون‌هایی که زنده‌اش می‌کنند قرنطینه و `/etc/SecCheck` کنار گذاشته می‌شود)، **سرویس‌های اسکنر** (`clamd@scan`، `clamav-freshclam`، `cxswatch`، `rspamd`، `spamd`) را متوقف و غیرفعال می‌کند، `ALL: ALL` فعال را در `hosts.deny` کامنت می‌کند، و IP سرور مقابل را در **CSF** whitelist می‌کند. **مقصد** علاوه بر این **لاگین root روی SSH** را باز می‌کند — که پیش از هر ری‌استارت با `sshd -t` اعتبارسنجی می‌شود و در صورت شکست تست، بکاپ برگردانده می‌شود. هر مرحله idempotent است و بکاپ نگه می‌دارد. داخل جریان sync، سورس prep خودش را اجرا می‌کند و بعد یک **بلوک آمادهٔ paste برای مقصد** (با IP سورس ازپیش‌پرشده) چاپ می‌کند و پیش از rsync منتظر Enter می‌ماند؛ `--skip-prep` روی سرورهای ازپیش‌آماده این مرحله را رد می‌کند. به‌تنهایی با `--prep` اجرا می‌شود (`--source`/`--destination` + `--peer-ip`)، یا گزینهٔ ۴ منو.

```bash
sudo ./magic-move.sh --source
sudo ./magic-move.sh --source --list-only --ns                          # فقط لیست اکانت‌ها + نیم‌سرورها
sudo ./magic-move.sh --source --list-only --with-sync                   # لیست اکانت‌ها، بعد rsync هوم‌هایشان
sudo ./magic-move.sh --sync -f magic-move/migration.csv --dest-ip 203.0.113.7 --dest-port 3131   # فقط سینک
sudo ./magic-move.sh --sync --skip-prep -f magic-move/migration.csv     # سینک؛ هر دو سرور ازپیش آماده‌اند
sudo ./magic-move.sh --prep --source --peer-ip 203.0.113.7              # prep این سورس + چاپ بلوک مقصد
sudo ./magic-move.sh --prep --destination --peer-ip 198.51.100.3        # prep این مقصد (root SSH را باز می‌کند)
sudo ./magic-move.sh --destination -f migration.csv
sudo ./magic-move.sh --destination -f migration.csv --protect "wp-rocket, litespeed-cache"
sudo ./magic-move.sh --destination -f migration.csv --no-plugin-heal   # فقط ترمیم PHP
sudo ./magic-move.sh --destination -f migration.csv --dry-run          # بررسی و گزارش، بدون تغییر
```

> ⚠️ روی مقصد، ترمیم **سایت‌های زنده را تغییر می‌دهد** — افزونه غیرفعال می‌کند و (روی CloudLinux) نسخهٔ PHP را عوض می‌کند. اول با `--dry-run` ببینید چه کاری *می‌خواهد* بکند. فایل CSV/گزارش/اسنپ‌شات‌ها نتیجهٔ کارند و در پوشهٔ خروجی می‌مانند؛ لاگ اجرا به `/var/log/magic-move/` می‌رود.
>
> ⚠️ مرحلهٔ PREP عمداً **امنیت سرور را برای مهاجرت کم می‌کند** — SecCheck و اسکنرها را خاموش می‌کند و روی مقصد root SSH را باز می‌کند. فقط بین سرورهایی که خودتان کنترلشان می‌کنید اجرایش کنید، و بعد از اتمام مهاجرت این محافظت‌ها را دوباره روشن کنید (بکاپ هر فایلِ ویرایش‌شده کنار اصل آن نگه داشته می‌شود).

## 📬 fix-roundcube.sh

**وب‌میل خراب Roundcube را روی سرور DirectAdmin از نو می‌سازد.** برای وقتی که وب‌میل خطای دیتابیس می‌دهد، صفحه سفید نشان می‌دهد، یا بعد از یک آپدیت دیگر کسی نمی‌تواند لاگین کند.

منو ندارد — یک کار را از اول تا آخر انجام می‌دهد:

۱. اطلاعات MySQL را از `/usr/local/directadmin/conf/mysql.conf` می‌خواند (لازم نیست رمزی تایپ کنید).
۲. **اول از دیتابیس Roundcube در `/root/` بکاپ می‌گیرد**، با تاریخ و ساعت. اگر بکاپ شکست بخورد هشدار می‌دهد و ادامه می‌دهد — چون نبودِ دیتابیس اغلب دقیقاً همان مشکلی است که دارید درستش می‌کنید.
۳. دیتابیس خراب را drop می‌کند و سوکت درست MySQL را خودکار پیدا می‌کند تا اتصال واقعاً برقرار شود.
۴. اگر فایل‌های باقیمانده در پوشه داده MySQL بمانند، آن‌ها را **فقط پس از اطمینان از خاموش‌بودن واقعی سرور** پاک می‌کند — هرگز فایل‌های دیتابیس را زیر سرور روشن حذف نمی‌کند (همان چیزی که باعث خطای `[1050] table already exists` هنگام rebuild می‌شد)، سپس MySQL/MariaDB را دوباره راه‌اندازی می‌کند.
۵. دستور `da build roundcube` را اجرا می‌کند — دایرکت‌ادمین Roundcube را تمیز از نو می‌سازد و در پایان نتیجهٔ صادقِ موفقیت/شکست را گزارش می‌دهد.

همه‌چیز در `/var/log/fix-roundcube/<timestamp>.log` لاگ می‌شود (با بازگشت به `/tmp`) و مسیر آن در پایان چاپ می‌شود.

> 📮 دیتابیس Roundcube فقط **مخاطبین، تنظیمات و ترجیحات پوشه‌ها** را نگه می‌دارد — نه خود ایمیل‌ها را. ایمیل‌های واقعی شما روی دیسک در mail store هستند و **دست نمی‌خورند**.

```bash
sudo ./fix-roundcube.sh
```

## 🔗 thing-to-link.sh

**هر چیزی را تبدیل به لینک دانلود می‌کند.** یک فایل روی سرور دارید و کسی لازمش دارد — مشتری، همکار، یا یک سرور دیگر. به‌جای دادن دسترسی SFTP، یک URL می‌دهید.

یک چیز می‌دهید (مسیر فایل، پوشه، یا URL)، بعد انتخاب می‌کنید **چطور** منتشر شود. فقط بک‌اندهایی که سرور واقعاً دارد پیشنهاد می‌شوند، به همین ترتیب — و **اولین موردِ در دسترس پیش‌فرض است** (Enter همان را انتخاب می‌کند؛ `--default` بدون منو همان را برمی‌دارد). اگر هیچ‌کدام نبود، اعلام می‌کند و متوقف می‌شود:

| روش | چه کار می‌کند |
| --- | --- |
| **web root** | کپی کلاسیک در `/var/www/html` که وب‌سرورِ درحال‌اجرا سرو می‌کند. **تا وقتی خودتان پاک نکنید می‌ماند.** وقتی وب‌سرور (یا `/var/www/html`) باشد پیشنهاد می‌شود. |
| **python link** | یک سرور یک‌بارمصرف پایتون روی **پورت آزاد تصادفی** که **فقط همان یک فایل** را پشت یک **مسیر توکن تصادفی** سرو می‌کند — نه کل پوشه، نه چیز دیگر. وقتی `python3` باشد پیشنهاد می‌شود. |
| **php link** | همان، با `php -S`. وقتی php-cli باشد پیشنهاد می‌شود. |

با `--web`، `--python` یا `--php` (یا `--serve php|python` و `--webroot <dir>`) مستقیم یکی را انتخاب کنید.

پوشه اول فشرده می‌شود (`tar.gz` / `zip`)؛ URL دانلود و بعد از روی سرور شما سرو می‌شود.

**لینک موقت (php/python) ناپایدار و خودمنقضی است:**

- **فقط یک فایل.** لینک `http://<ip>:<port>/<token>/<file>` است؛ هر مسیر دیگری — از جمله `/` — می‌شود `404`. نه لیست دایرکتوری، نه چیز دیگری روی دیسک که قابل دسترسی باشد. `Range` پشتیبانی می‌شود، پس دانلودِ نیمه‌کاره قابل ادامه است.
- **پورت فایروال تا پایان اجرا باز و بعد بسته می‌شود** — `firewalld` / `ufw` / `iptables` خودکار تشخیص داده می‌شود، rule برچسب یکتا می‌گیرد، و هنگام پایان **دقیقاً همان rule حذف و سپس بازبینی می‌شود**، پس هیچ پورت بازی باقی نمی‌ماند.
- **فقط تا وقتی اجرا زنده است دوام دارد.** با `Ctrl+C`، با قطع سشن SSH (`SIGHUP`)، یا با `--timeout` که تعیین می‌کنید (پرسیده می‌شود؛ **سقف ۱۲ ساعت**) همه‌چیز جمع می‌شود: سرور متوقف، فایروال بسته، فایل‌های موقت پاک. موقع timeout اول جلوی اتصال‌های جدید گرفته می‌شود و به دانلودِ درجریان فرصت اتمام داده می‌شود. یک backstop پس‌زمینه حتی اگر اسکریپت با `kill -9` کشته شود پورت را می‌بندد.

```bash
sudo ./thing-to-link.sh
# یا با پرچم‌ها همهٔ ورودی‌ها را از اول بدهید:
sudo ./thing-to-link.sh -i /root/backup.tar.gz --default        # اولین بک‌اندِ در دسترس
sudo ./thing-to-link.sh -i /root/backup.tar.gz --php -t 2h
sudo ./thing-to-link.sh -i https://example.com/file.zip --python
sudo ./thing-to-link.sh -i /home/user/backups -c zip --webroot /var/www/html   # کپی کلاسیک وب‌روت
```

هر پرچمی که ندهید، همان به‌صورت تعاملی از شما پرسیده می‌شود. برای دیدن فهرست کامل `./thing-to-link.sh --help` را اجرا کنید.

> ⚠️ هر چیزی که منتشر می‌کنید تا وقتی لینک بالاست **برای هر کسی که لینک را داشته باشد قابل دسترسی است.** لینک موقت این ریسک را محدود می‌کند — پورت تصادفی، توکن غیرقابل‌حدس، و با سشن یا timeout می‌میرد. ولی کپی **web root** تا وقتی از `/var/www/html` پاکش نکنید عمومی می‌ماند، پس بکاپ‌ها و فایل‌های دیتابیس را بعد از اتمام کار پاک کنید.
>
> ℹ️ لینک موقت را **داخل `tmux`/`screen`** اجرا کنید و با قطع SSH می‌ماند (چون دیگر سشن شما نیست که تمام می‌شود) — ولی `--timeout` همچنان می‌بنددش.
